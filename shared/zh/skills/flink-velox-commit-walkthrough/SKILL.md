# flink-velox-commit-walkthrough

## 核心原则

1. 一commit一文件、按仓分目录——检视者按仓取阅，commit与文档一一对应。
2. 自包含——走读脱离开发会话仍可独立检视：调用链、数据流与设计依据内嵌在文档里，不留上下文断层。
3. 片段-解析配对——每个关键代码片段必须配解析；只摘承载决策的区间，不整文件搬运。
4. 要点化表述——解析以要点为单位，一要点一信息；抑制冗余叙述与无信息量的复述。
5. 信息密度——每条解析直指一处设计决策或行为变化；模板化套话（"该函数实现了其功能"式）一律不写。

## 触发时机

代码评审（CODE_REVIEW.md）通过后、用户门禁2呈报前，由developer执行。返工的修复amend进引入问题的对应commit（id重生成，不新增修复commit），受影响走读文件原地刷新（H1与门禁清单中的id随之更新），IMPLEMENTATION.md覆盖声明同步更新。呈报时走读文件逐行列入门禁2材料清单（仓库、commit短哈希与标题、文件路径），并逐commit呈报确认——每份先呈大体内容行（短哈希、标题、变更主旨一句话）供用户核对文件与commit对应无误，再检视该文件、逐个确认放行。

## 产出布局

```text
tasks/<task-name>/commits/
  velox/01-<slug>.md
  velox4j/01-<slug>.md
  gluten/01-<slug>.md
```

只覆盖任务产生的commit——范围取`git log <基线>..HEAD`，基线用TASK_STATE记录的任务起点；仓库无改动则无该目录。文件名带两位序号前缀，按commit先后从01递增（`git log --reverse <基线>..HEAD`的顺序），序号即检视顺序；文件名不带commit id——id只在文件内H1与门禁2清单中标识，amend后id变化无需重命名，仅rebase改变顺序时重排序号。

## 内容规格

**变更主旨**：概括变更意图（实现能力/修复缺陷/结构调整）、动机（对应SPEC或设计的哪一项、由什么触发）与达成的行为变化。commit改变或完善了执行流程、数据通路、生命周期时序的，在此之外单列**流程影响**：流转前后差异、新路径接入点。

**片段走读**：每个关键片段配三要素解析——

- 改动内容：该片段改了什么，与新行为的对应关系；
- 作用与意义：为什么值得改、解决了什么问题、在哪条链路上生效；
- 实现思路：为什么这么改——方案取舍与依据（对照设计文档或契约）。

**调用链上下文**：标出片段在调用图中的位置——上游调用方、本片段职责、下游被调方，以及数据自哪来流向哪；原则是让每段实现代码的上下文背景完整可见，检视者无需回溯会话即可定位它在系统中的角色。

**组织结构**：片段按架构层次递进组织（自顶向下沿调用方向，如planner改写→跨语言计划节点→native算子生命周期→状态存取）；commit内各片段无层次依从关系时按变更内聚性平铺，不强行排序。

## 文件骨架

```markdown
# <short-hash> <commit标题>

## 变更主旨

<意图、动机、行为变化；对应SPEC/设计的锚点>

## 流程影响（涉及流程改变或完善时才设此节）

<执行流程/数据通路/时序的流转前后差异、新路径接入点>

## 片段走读

### <层次名或主题>（按层次递进；无层次关系则按内聚性平铺）

```<lang>
<代码片段——只摘承载决策的关键区间>
```

- 改动内容：<what>
- 作用与意义：<why>
- 实现思路：<how与取舍>
- 调用链：<上游→本片段→下游；数据流向>
```

## 输入契约

必需：任务分支commit清单（`git log --oneline <基线>..HEAD`）与各commit的diff。建议：DESIGN.md（层次组织与实现思路的依据）、IMPLEMENTATION.md（改动分组对照）。

## 输出契约

每commit一份md，按仓分目录落`tasks/<task-name>/commits/`。每份覆盖该commit全部关键片段，片段配三要素解析与调用链上下文；不整文件粘贴、不堆模板化表述。全部走读完成后在IMPLEMENTATION.md追加覆盖声明（仓库×commit数×文件数）——该声明是门禁2材料清单的数据源，逐commit文件均可在其中定位。
